# 测试维护规范

## 目标

测试保护可持续的行为合同。评价依据是能发现的回归、定位能力、运行成本和变更成本，不以测试数量增长作为成果，也不以数量下降作为精简成功的唯一依据。

## 新增前判断

1. 明确测试防止什么实际故障，失败会影响哪项用户行为或数据完整性。
2. 查找现有模块覆盖：已有同层同语义断言时补充原用例，只有独立故障场景才新增测试；不同生命周期或不同事务入口不因名称相似而合并。
3. 判断是否跨本次任务仍有维护价值。核心规则、失败回退、旧档迁移、输入可达、资源 / Session 隔离、数据路径安全通常长期保留。
4. 选择最低有效层级：纯规则优先 EditMode；真实输入、Unity 生命周期和界面布局使用必要的 PlayMode；构建 / 真机验收保存当次证据，不能通过读取旧成功 JSON 宣称当前构建成功。

临时验证包括一次性发布版本检查、迁移前后资产路径对照、探索脚本、临时截图 / 诊断。此类验证完成后清理代码、`.meta`、无消费者夹具和临时输出，将必要结论或原始证据放入文档归档。历史存档样本是长期兼容性输入，不属于应清除的一次性迁移工具。

## 长期套件规则

- 按模块和行为命名新增测试；已有版本前缀不自动代表无用，也不为去掉前缀制造大批无功能重命名。
- 保留精确的算法预期、事务最终态、稳定序列化身份和正式资产家族规格。避免锁定阶段版本号、旧工作台结构、生成日期、配置字段总数及已经退役的临时资产路径。
- 配置与架构策略验证必须有实际规则、真实扫描范围、负例和有用的错误信息。正式配置全量校验只保留一个主要测试入口，局部测试用于独特的生成或消费行为。
- UI 验证优先真实输入与可见结果，包括焦点、唯一高亮、命中、边界、文本和暂停；不检查某个 Controller 是否包含指定代码行。当前常规视觉矩阵为 1920×1080 × 中文 / 英文 / Pseudo Locale。
- 不为减少启动次数把所有独立场景塞进一个巨型测试。只合并同一合同、相同前置且没有新增故障分支的重复检查；失败仍应指出具体对象 / 场景。
- 断言配置数量时先判断是否本身就是产品合同；能通过非空、完整登记、合法引用、每部位覆盖等表达时，不再重复一份内容清单。
- 测试须使用隔离的数据根，完整恢复场景、分辨率、输入设备、时间、Locale、临时文件及资源。结束后恢复项目基线 Reload Scene Only：`EnterPlayModeOptionsEnabled = true`、`EnterPlayModeOptions = DisableDomainReload`（数值 `1`）；专项矩阵可以临时切换，见[兼容检查](../infrastructure/domain-reload-compatibility.md)。
- 第三方包 / 供应商测试由上游维护，不删除包缓存来降低数量。常规项目回归限定两个 `DarkFlare.Tests.*` 程序集；修改相关包集成时再运行针对性上游测试，既有 Ignore 与项目失败分别报告。

## 收尾检查

- 对新增及受影响测试逐项决定长期保留、合并或清除；清理删除测试独占的辅助函数、常量、using、`.meta` 与无用数据。
- 记录删除原因及被保留的覆盖位置；不得通过删除失败用例、降低有效断言或增加 Ignore 掩盖真实缺陷。
- 运行与变更相称的验证；清理整套测试时运行项目 EditMode / PlayMode，保存实际计数和失败情况。既有失败必须与清理引入的失败区分。
- 更新当前测试入口及适用范围，历史验收数字和日志保留原意，不要求旧发布证据的源码路径永远存在。
