# Alpha 0.5：地图数据与地表方案

状态：部分实现。2026-09-18 已完成数据与导入，当前 V1 见[地图文档模块](../../maps/README.md)；本方案中的渲染、静态几何和运行时地图管理仍待实施。上级入口：[总计划](../alpha-0.5-plan.md)。

## 权威数据与派生资产

地图以 `Assets/Data/Maps/<name>.dfmap` 为唯一可编辑布局源，内容为 JSON、UTF-8 / LF，具有独立格式版本与稳定内容 ID。专用后缀用于 Unity 导入，普通 `.json` 用于交换；类型命名空间、数据 V1 与导入合同见[首轮细化归档](../archive/alpha-0.5.0-map-foundation-contract.md)。Unity ScriptedImporter 将其导入为只读 `MapDefinition` ScriptableObject；地表、Wang 规则、障碍、装饰、交互及区域类型仍使用 Odin 中文字段的 ScriptableObject 配置，通过 ContentId 引用。

编辑器修改内存文档并保存 JSON，不能同时维护一份可独立修改的布局 SO。JSON 不存 Unity Instance ID、GUID、Sprite 索引、场景层级路径或生成后的 Tile 编号。Importer 注册稳定子资产标识，重复导入保持 `.meta` / 子资产引用；内容目录和 Addressables 只引用导入产物与正式定义。

流程：`地图源文档 → 结构 / 语义校验 → 不可变运行时地图 → 地表显示、碰撞、导航、出生和交互`。编译结果带源 Hash、规则版本与内容依赖版本，缓存失效可完全重建；不能从场景 Renderer 反推权威地图。

分层建议：MapModel 持有活动地图身份、语义差量和修订；MapSystem 管理合法修改及派生结果提交；纯 MapCompiler / TerrainResolver 不依赖场景；地图显示 Controller 读取快照并监听事件，不直接写 Model。编辑器的 MapEditService 复用纯文档规则，不创建玩法 Session。地图切换由既有 Scene Flow 编排，导航只消费地图快照，不反向修改地表。

## 数据分层

| 数据 | 主要字段 | 规则 |
| --- | --- | --- |
| 地图头 | formatVersion、mapId、revision、seed、origin、cellSize、width、height、terrainSetId | 格式版本、地图内容修订、运行时地图 generation 分开；坐标有限、尺寸有上限 |
| 地表 | terrainPalette、chunks、稀疏 variantOverrides | 每逻辑格一个稳定 TerrainId；块内按固定行序保存，首期块边长建议 32；未列块使用明确 defaultTerrainId |
| 障碍物 | objectId、definitionId、位置、合法旋转、状态 | 定义声明地面占用轮廓、碰撞类别、导航阻挡和遮挡分段；不从美术 Alpha 猜碰撞 |
| 装饰物 | objectId、definitionId、位置、旋转、variantId | 默认无碰撞；需要阻挡的对象必须显式引用障碍能力，不能仅因画得像石头就阻路 |
| 交互点 | objectId、definitionId、位置、入口 / 目标绑定 | Merchant、Crafting、MapExit、PlayerSpawn 使用类型化配置；传送目标为 MapId + EntryId |
| 区域 | regionId、definitionId、几何、priority、tags、类型参数 | 首期矩形和简单多边形；支持可玩区、刷怪区、禁刷区；冲突按优先级、稳定 ID 解析，禁止区优先 |

对象有一种记录身份，可由定义组合渲染、障碍与交互能力，避免“同一商人既是障碍记录又是交互记录”产生两份对象。地图内 ID 唯一，跨地图使用 `MapId/ObjectId`；AI Upsert 不改变原身份。

region 与 object 引用均通过目录登记验证。自交多边形、空区域、重复 ID、未知 ContentId、非法缩放 / 旋转和越界占用均返回定位信息，不静默修正。地图版本变化引起旧运行状态落点失效时执行明确迁移，不靠导入器随机找位置。

## 坐标与 Dual Grid

地图位于 Unity XY 平面，Z 只承担摄像机 / 渲染既有用途。逻辑单元 `(x,y)` 中心为 `origin + ((x+0.5),(y+0.5)) × cellSize`；世界转格使用 floor，覆盖负坐标与原点偏移，外侧不是有效通行格。

显示网格相对逻辑单元中心偏移半格。显示块 `(x,y)` 中心为 `origin + ((x+1),(y+1)) × cellSize`，四角分别读取：

```text
NW = T(x, y+1)      NE = T(x+1, y+1)
SW = T(x, y)        SE = T(x+1, y)
```

Corner Wang Key 固定按 `NW, NE, SE, SW` 编码；对单材质二元遮罩，对应位为 `1, 2, 4, 8`。修改一个逻辑格只影响四个相邻显示块及其所在 chunk；chunk 边界读取相邻一圈数据，不能自行把块外当空白。

地图外虚拟样本由边界规则提供视觉材质，导航一律不可通行；显示边缘最多向外延伸半格，由不可玩边界与镜头覆盖合同控制，不把额外显示范围当可玩区。四边、四角及负坐标都必须有一致结果。

建议技术样例先用 `cellSize = 1`；导航分辨率允许为其整数细分，根据已测角色半径 0.30–0.36，首轮优先验证每逻辑格 4×4 个导航格（子格 0.25），并与 2×2 比较窄路误判；最终根据安全边距与可达性实测冻结。现有 8 单位地砖不作为新逻辑网格大小。

Dual Grid 的偏移和四角选择可参考[原理说明](https://www.boristhebrave.com/2023/05/31/quarter-tile-autotiling/)；本项目仍采用用户指定的 Dual Grid，不改用文中的 quarter-tile 替代方案。

## 四种材质与 Wang 覆盖

泥土、草地、水、道路是地表语义。变体只是视觉差异，不能改变通行、代价或地图连通性；未来需要湿泥等不同通行属性时，应另建地表定义或显式区域规则。

二元 Corner Wang 有 16 种四角模式，但四材质完整四角组合为 `4^4 = 256`。不能把“四类各 16 张”直接当成已经解决所有三 / 四材质交界。[Tiled Corner Set 文档](https://doc.mapeditor.org/en/stable/manual/terrain/)可用于核对角标记及模式覆盖。

采用完整四角 Key 解析，配合可复用的材质纹理与拓扑遮罩编译，避免要求人工逐张绘制 256 套过渡：

1. Wang 配置为每个角模式定义标准覆盖区、边缘采样及转角拓扑；各材质读取自己的四角二元掩码。
2. 多材质编译器将覆盖区组成完整分区：每个像素归属明确、无孔洞，混合边的权重总和为 1，四角只出现指定材质；中心并列用固定规则处理。
3. 共享边只由该边两端的地表和声明的边签名决定，不能受另两角、渲染顺序或单块随机数影响。三 / 四材质中心可以不同，边界必须一致。
4. 最终每个支持的 Key 都有明确 Tile 结果；可由导入工具从批准的独立纹理与遮罩确定性编译为独立 Sprite / Tile 资产。不能在缺规则时悄悄替换成泥土或有缝贴图；技术阶段可显示诊断色，正式发布校验必须拒绝缺失。
5. 首阶段先验证两材质、三材质、四材质十字、孤点、一格路、内外角及对角鞍点，再扩大正式资产。四种材质的 256 Key 是算法覆盖要求，不是强制每 Key 都有多个手绘变体。

技术样例使用可验证的参考分区：显示块内局部坐标 `(u,v)` 的四角权重为 `((1-u)v, uv, u(1-v), (1-u)(1-v))`，按 TerrainId 汇总，最大权重决定材质，等值按固定规则。该定义保证共享边仅依赖端点；正式 Wang 遮罩可以细化内部形状，但必须保持角 / 边采样合同。材质纹理变体共用边界采样带；不能只保证遮罩无缝却让两侧纹理亮度跳变。分区在相同精度下生成渲染与几何，导航再执行半径安全内缩。

对角鞍点固定采用“同材质对角区域不以零宽连接互通”；需要连通就绘制具有宽度的相邻格。道路的十字 / 丁字 / 转角由地表覆盖区域自然产生，首期不额外引入 Edge Wang 路网或第二份道路连通数据。

## 变体与资产合同

- 以 `MapSeed + 显示坐标 + WangKey + VariantSetId` 的稳定 Hash 选取变体；无关位置编辑不重掷全图，不使用战斗 / 掉落随机通道。
- 手工指定变体使用稳定 VariantId；规则变更后不再兼容的 override 报告冲突，不默默重选。
- 首批建议每种纯地表至少两个可观察变体，过渡内部也可扩展变体；所有可互换成员保留同一角 / 边签名。第一版先只改变内部，外边采样带固定，不增加边随机组合。
- 运行时使用 Tilemap Chunk 批量渲染，不为每格创建 MonoBehaviour。资产可由 Unity SpriteAtlas 打包，但源文件仍一张 PNG 对应一个 Sprite，不制造生产 SpriteSheet 或手工切图流程。
- 按 [unity-2d-sprite-workflow](../../../../.agents/skills/unity-2d-sprite-workflow/SKILL.md) 冻结参考、固定画布、PPU、Pivot、Point / 压缩 / Alpha、共享边宽度与相机尺度。当前阶段不假定旧 512×512 地砖可直接缩成新地表。
- 0.5.0 中先测量现有角色与镜头尺度、批准一个地表 Pilot，再冻结正式像素尺寸并扩展材质。生成源图和编译输出逐个审计，保留接缝量化与可见截图；无需本轮生成美术。

## 碰撞与导航同源

地表编译同时给出连续覆盖轮廓和通行语义；水岸阻挡根据同一拓扑生成，不从 Sprite Alpha 或变体纹理临时读取。碰撞轮廓、障碍 footprint 与导航栅格共用地图原点 / 单位和版本。

导航格按“单位足迹是否完全落在可通行空间”保守标记，组合水域、障碍、边界和区域；按不同 Agent 半径计算净空，不能仅以中心点是否在草地上判定。可走区域相对视觉边界的安全内缩必须可显示和测量，不能出现隐形大墙或角色明显踏水。

障碍按接地点 footprint 布置；高树冠不扩大地面阻挡。必要的 CompositeCollider2D / 网格代价均由编译结果构建。地表变体变化只刷新显示；阻挡 / 通行规则变化才增加导航修订。动态地图编辑的更新先准备完整派生快照，再一次切换有效版本。

## 必须验证

固定种子重现、导入 / 导出往返、全部四角 Key、任意兼容边的跨变体接缝、鞍点连通、边界 / chunk 接缝、非法数据、缺内容拒绝、增量重建与全量重建等价。导航与物理在水岸、斜角、树干、一格通道的可通行结论一致。

规模建议：城镇先以 64×64 逻辑格、野外 128×128 建样例；以 256×256 逻辑格作为编辑与导航压力输入。它们是工程起始配置，最终地图尺寸与实际通道宽度在 0.5.0 尺度验收后确定。
