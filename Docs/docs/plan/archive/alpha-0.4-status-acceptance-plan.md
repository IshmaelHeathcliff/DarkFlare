## 执行顺序

### 1. 核对合同与覆盖

- 将[验收矩阵](./status-system/integration-and-validation.md)逐项对应到现有状态、战斗、存档、生命周期及 UI 测试，标明已覆盖、需补验证和实际缺陷。
- 核对用户确认的抗性、满层策略及三档显示规则。隐藏仅影响视图，不能改变状态效果、驱散或存档。
- 审查后续物品所需的 Apply / Dispel 准备、提交、回退及延迟通知接点；只补状态合同缺口，不提前实现物品事务。
- 正式来源样例尚未默认进入常规战斗。验收使用明确的受控来源，区分接口样例与正式玩法，不擅自调整掉落或平衡配置。

完成条件：每项合同有代码 / 测试依据或明确待验证项；不为增加测试数量重复已有断言。

### 2. 复核最终界面与输入

- 对最终右上角 HUD 和状态窗口检查 1920×1080 中文、英文、Pseudo，以及 1280×720 的拥挤场景；验证多状态换行、隐藏开关、长详情滚动及浮窗边界。
- 验证显示 / 可隐藏 / 从不显示；切换后两入口一致、图标消失后焦点有效、重新显示可达。
- 验证鼠标悬停、键盘 / 手柄导航与确认返回、设备切换、暂停和恢复。Gameplay 不启用 UI Navigate 抢占移动。
- 以真实效果核对层数、最近到期时间、最强候选与独立层详情；暂停期间不倒计时，驱散后不残留浮窗。

完成条件：最终布局与输入可用；截图保留到验收目录，临时采集代码不留作长期套件。

### 3. 独立 Windows Player 验收

- 先确认构建与启动工具、可见界面控制方式以及存档 / 设置隔离方案。当前默认路径来自 Application.persistentDataPath，不能假设存在数据根命令行开关；必须验证隔离后才能运行写档流程，不覆盖真实玩家数据。
- 构建当前代码和 Addressables，在独立 Player 中验证启动、正式图标加载、HUD、状态窗口及键鼠 / 手柄输入。若缺少可见控制能力，明确记录缺口，不以 Editor 截图代替 Player 验收。
- 通过受控验收数据或仅供验收构建使用的入口验证：施加与叠层、自然到期、消耗 / 驱散、眩晕行动限制、周期伤害与死亡；沿用统一 Command / System，不另写玩法逻辑。
- 验证保存、退出、继续后状态数值与周期相位保持，无离线补跳；装备持续来源不重复；返回主菜单再开 Session 不串状态。
- 保存构建结果、关键操作记录、截图和日志；区分项目错误与既有第三方警告，查明影响后再给出结论。

完成条件：独立 Player 实际运行通过上述链路，隔离数据可确认；验收入口与临时配置收尾清理。

### 4. 回归与交付

- 缺陷修复优先扩展已有模块测试，保留事务回退、历史迁移、输入可达和 Session 隔离等长期保护。
- 全量运行项目两个 EditMode / PlayMode 程序集，记录当次实际结果，不以历史计数判定成功。检查 Reload Scene Only 基线和测试资源清理。
- 通过验收后更新运行版本为 `0.4.1-alpha`；若无持久化结构或内容兼容变化，保持 core v4、Schema 3。版本改动后的最终构建须确认版本与启动结果。
- 更新状态、战斗、HUD、输入、存档及配置文档，清理临时测试和无关自动序列化噪声；证据存入 `Docs/docs/assets/acceptance/alpha-0.4-status-acceptance/`。
- 将状态总计划、本计划及配套计划文档归档并修正链接，模块文档保留实际 API 和边界；更新项目索引，随后将统一物品使用计划标为下一阶段待执行。
