# 游戏设计

## 边界检查

1. 确认用户显式调用了 `/design` 或 `$design`。
2. 确认任务目标是游戏设计，而不是开发或实现。
3. 若任务包含编码、场景或 Prefab 编辑、资源制作、技术架构、调试、测试等开发工作，立即停止本 Skill，不读取或修改 `Docs/design/`，并请用户将游戏设计与开发任务拆分。
4. 将所有写入严格限制在仓库根目录的 `Docs/design/` 内，且只创建或修改 Markdown 文档。不得修改代码、配置、资源、场景、Prefab、`Docs/docs/` 或其他目录。

## 工作流

1. 先检查 `Docs/design/` 的目录结构和相关设计文档，避免重复或冲突。
2. 从玩家目标、核心体验、规则、反馈、失败与成功条件、键鼠和手柄操作等角度识别设计约束。
3. 对不明确且会显著改变设计方向的问题，先提出异议或请求用户决策；其余细节采用最小、可逆的假设并明确标注。
4. 先给出简短计划和成功标准，再进行精准修改。
5. 优先更新已有模块文档；仅在没有合适归属时新建文档。保持文档模块化，避免单文件过长。
6. 记录已确定的规则、关键取舍、待验证假设和开放问题。不要把未经确认的设想写成既定事实。
7. 修改后复查文档之间的一致性，并确认变更没有超出 `Docs/design/`。

## 输出要求

- 使用中文、UTF-8、LF 和 Markdown。
- 以玩家体验和可验证的设计目标为中心，避免把技术实现细节写入设计文档。
- 清楚区分“已决定”“待验证”和“开放问题”。
- 最终说明修改了哪些设计文档、形成了哪些决策，以及仍需确认的事项。
